## What Went Well

1. Scope discipline remained strong.
   - Each story stayed inside its intended slice.
   - Important-task behavior was correctly deferred to Epic 3.
   - Confirmation dialogs, undo, filters, counters, backend behavior, and new dependencies were avoided.

2. Architecture consistency held across all stories.
   - The approved task schema remained unchanged: `id`, `title`, `completed`, `important`, `createdAt`, `updatedAt`.
   - The app continued using one runtime task array as the source of truth.
   - Active and Completed lists were derived from the task array rather than persisted separately.
   - The localStorage key remained `smiple-todo.tasks`.

3. Persistence was implemented cleanly and reused consistently.
   - Story 2.1 established `loadTasks()` and `saveTasks(tasks)` in `src/storage.js`.
   - Later stories reused the same full-array persistence pattern after valid mutations.
   - Invalid, malformed, unreadable, or schema-invalid storage data fails safely to an empty array.

4. DOM-safe rendering stayed consistent.
   - Task titles from input and localStorage continued to be treated as user-provided text.
   - HTML-like task titles were verified as literal text after add, edit, completion, deletion, and refresh flows.

5. Verification quality was strong.
   - Every story recorded `npm test` and `npm run build` passing.
   - Browser verification was performed for each interactive UI story.
   - Manual checks covered persistence, keyboard behavior, empty states, responsive layout, safe text rendering, and no task-storage network calls.

6. Lightweight test strategy continued to work.
   - Node's built-in test runner remained sufficient for domain logic, storage behavior, validation, and render view-model contracts.
   - No new test framework or browser DOM dependency was introduced.

## Challenges and Growth Areas

1. UI behavior still requires browser verification.
   - Focus behavior, keyboard reachability, localStorage persistence across refresh, and responsive layout cannot be fully proven by the existing Node tests.
   - Browser verification should remain mandatory for Epic 3 because it adds more interactive task controls and visual state.

2. The existing Important action is visible but intentionally not functional yet.
   - Earlier stories established the `data-action="toggle-important"` control pattern.
   - Epic 3 must wire this action carefully without disturbing edit, complete, delete, persistence, and completed-section behavior.

3. Dependency advisories remain outside feature scope.
   - The Epic 1 retrospective flagged Vite audit advisories as separate maintenance work.
   - Epic 2 correctly did not force dependency upgrades during feature delivery.
   - This remains a medium-priority maintenance item, not a blocker for Epic 3.

4. Render and event orchestration now cover more states.
   - The app supports add, edit, complete, delete, Active rendering, Completed rendering, validation state, and persistence.
   - Epic 3 should avoid broad rewrites and instead extend the established flow.

## Story-by-Story Notes

### Story 2.1: Persist Tasks in Browser Storage

Key outcomes:

- Added `loadTasks()` and `saveTasks(tasks)` in `src/storage.js`.
- Initialized runtime task state from localStorage.
- Saved the full task array after valid task creation.
- Added strict saved-task schema validation.
- Verified first load, valid add persistence, refresh restore, corrupt storage fallback, safe text rendering, and no network storage.

Learning:

- Persistence behavior is central to every later mutation, so keeping it isolated in `src/storage.js` prevented duplication.

### Story 2.2: Edit Existing Task Titles

Key outcomes:

- Added immutable task title editing.
- Preserved schema and refreshed only `updatedAt` for valid edits.
- Added active-row edit state with Save/Cancel controls and inline validation.
- Escaped task IDs before focus query selectors.
- Verified valid edit, invalid edit, correction, cancel, persistence after refresh, keyboard reachability, mobile layout, and HTML-like title safety.

Learning:

- Edit mode introduced UI state that must remain separate from persisted task records.

### Story 2.3: Complete Tasks into Completed Section

Key outcomes:

- Added immutable completion logic and `getCompletedTasks`.
- Rendered Completed tasks dynamically from the single task array.
- Added visible Completed status text so completion is not communicated only by color or line-through.
- Verified completion, persistence, empty-state toggles, keyboard activation, safe text rendering, and responsive layout.

Learning:

- Completed is a derived section, not a separate persisted list. This kept persistence simple and aligned with architecture.

### Story 2.4: Delete Tasks from the App

Key outcomes:

- Added immutable deletion with `deleteTask`.
- Wired Active and Completed delete actions through delegated handlers.
- Added completed-task delete controls with task-specific accessible labels.
- Verified active deletion, completed deletion, localStorage removal, refresh persistence, empty states, keyboard flow, safe text rendering, and responsive layout.

Learning:

- The existing `data-action` and `data-task-id` pattern scaled well from Active actions to Completed actions.
